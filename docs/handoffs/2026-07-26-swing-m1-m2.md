## M1 — the catch-up can starve the 15-second SL/TP scheduler

`SwingBatchCatchUp`'s `@Scheduled` is unqualified, so it runs on the single DEFAULT scheduler it
shares with `PaperScheduler` (the 15 s SL/TP loop). The sweep does synchronous multi-session DB +
HTTP work, the funnel requests have no explicit timeout, and the market-hours check runs only at
ENTRY so a sweep that starts before the open keeps running past it.

Three parts, all required:

1. **Dedicated scheduler.** Bind the catch-up to its own single-thread scheduler. Precedents in this
   repo, follow their shape and their javadoc style: market-data's `MonitorSchedulingConfig` has
   `barFlushTaskScheduler` and `oiCaptureTaskScheduler`, each with a comment explaining why it is not
   on the default pool and why not on the monitor pool. Starving the default pool is the S1–S3
   failure mode (#1016) and it has bitten this repo repeatedly.
2. **Explicit funnel timeouts.** `ManasFunnelClient` and `MinerviniFunnelClient` need connect AND
   read timeouts. An unbounded read is what turns a slow screen into a held thread.
3. **Abort at the market-open deadline MID-RUN**, not only at entry. A sweep must not still be
   replaying history when the session opens — check the deadline between sessions and stop cleanly,
   leaving remaining rows non-terminal so the next sweep picks them up (C3's union already guarantees
   they are not lost).

Keep `SwingRunMutex` for run serialisation — do not replace it with the scheduler's single thread.

## M2 — the emergency close path does unrelated work first

`PaperController` (the manual-close endpoint) calls the full `positionDetail()` merely to obtain the
BOOK. That path does instrument-metadata HTTP and other reads inside `PaperService`, so an emergency
explicit-price close can hang or fail before it ever reaches `closePosition`.

Get the book from a lightweight local position query. Keep the audit enrichment AFTER the close — the
close is the urgent part; the audit detail is not.
