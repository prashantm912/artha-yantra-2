# 2026-08-02 — M36 / M37 backtest A/Bs (E4 decision sheet follow-up)

Owner-commissioned evidence for the two E4 sub-items the 2026-08-01 decision sheet declared **not
decidable without a backtest A/B** — M36 (Minervini 50-day-MA trail arms day-1) and M37 (Power Play
thrust has no adjacency window). Method reproduced from the M39 precedent
(`docs/strategies/m39-vcp-caps-backtest-2026-07-06.md`): a deploy-free geometry check where one is
cheap and informative, then a deep backtest A/B over the live `candles`@1d equity universe using the
production `MinerviniBacktestService`/`MinerviniSwingBacktest`/`VcpDetector` classes unmodified except
for two small additive static toggles (default-off, so the baseline arm is byte-identical to
production — see §0). No production code, strategy config, or `.env` was changed; nothing is armed.
Every claim below is tagged **[computed]** (derived here from code/config/DB I read on this
checkout), **[sourced]** (quoted from a cited doc/PR), **[recalled]** (memory, not re-verified in this
pass), or **[assumed]** (an inference I could not fully verify). A claim computed from an assumed
input stays **[assumed]**.

## Read this first — the bottom line

**M36 — recommend KEEP the current arm-day-1 trail; do not ship the tested fix.** The audit's
premature-whipsaw concern is real (disarming the trail until the 50-day MA rises to the entry level
raises per-trade win-rate and expectancy, consistently across all 4 Minervini setups), but on the
metric this repo already treats as decision-relevant — the realistic-live, cost-net, slot-limited
portfolio — the fix makes things **worse**, not better (max drawdown 58.86%→74.33%, Sharpe 0.75→0.67).
A higher-CAGR, worse-tail-risk trade is not an unambiguous win, and the change is effectively a
loosening of an early protective exit trigger, so the burden of proof is on it — it does not clear
that bar as tested.

**M37 — recommend REJECT any thrust-adjacency cap; do not add one.** The audit's concern (a thrust
from years before the current base still counts) is confirmed as real and much bigger than a
same-day snapshot suggested, but restricting it does not help: at both magnitudes tested (30 and 90
trading sessions), the realistic-live Sharpe falls monotonically as the cap tightens
(0.75 baseline → 0.70 at 90 sessions → 0.63 at 30 sessions) and CAGR falls in both cases too. The
current unconditional thrust check is not the liability it looks like on paper — removing the
"stale-thrust" trades removes trades that were net-additive to the realistic portfolio, the same
shape of mistake M39 found in the VCP duration floor.

## §0 — Method: harness reuse, not reimplementation

Reusing the exact production classes (rather than reimplementing the VCP geometry / swing-sim logic)
was a deliberate choice to avoid the "surprising number → suspect the harness" trap. Two small,
additive, default-off static toggles were patched into the worktree for measurement only (never
committed, reverted before this PR):

- `VcpDetector.thrustAdjacencyDaysOverride` (int, default `0` = disabled): when `>0`, `thrust()`
  additionally requires the qualifying high to sit within that many sessions of the base start
  (`VcpDetector.java:151-166` on `origin/main` is the untouched method this wraps).
- `MinerviniSwingBacktest.armTrailAtEntryOverride` (boolean, default `false` = disabled): when
  `true`, the 50-day-MA trail stays inert per-trade until `sma50 >= entrySignalClose` at least once
  since entry (`MinerviniSwingBacktest.java:240-250`, the `exitFires` method, is the untouched logic
  this wraps).

**[computed]** Both toggles default to the CURRENT live behaviour, and the harness reproduced
identical numbers from two independent JVM invocations run ~20 minutes apart with the toggles at
their default (disabled) value: `vcp` trades=7582, win%=32.4716, payoff=4.1756, exp%=4.4532,
stopOut%=27.9610; `portfolioFIFO` cagr=22.90/maxDD=43.74/sharpe=0.63; `portfolioRsPriorityNet`
cagr=28.58/maxDD=58.86/sharpe=0.75 — matched to the last printed decimal both times. This is the
"re-run the control, confirm it reproduces to the decimal" check the task brief requires, satisfied
before any delta below is trusted.

**[computed]** For M37, the three setups NOT gated by `thrust` (`vcp`/`primary-base`/`cheat-3c`)
reproduced byte-identical trade/win%/payoff/exp%/stopOut% figures across every run — confirming the
adjacency toggle touches only what it should (those three never call `thrust()`; only `power-play`'s
entry gate reads it). **M36 has no equivalent in-family control** — all 4 Minervini setups share the
same `trailing_stop basis=indicator` exit, so the arm-toggle affects all of them (confirmed: every
setup's numbers move in §1c) — see Open Doubts §2 for how harness confidence is established instead.

**[computed]** Run parameters, matching the live defaults exactly (no `application.yml` override
exists for either): `VcpDetector` = zigzag 2.5%, contractions 2-6, ratio 0.2-0.9, final-vol-low 0.5,
cheat-fraction 0.5, thrust 100%/40-session window, depth cap 60%, base-weeks `[0,65]` (M39's floor
stays disabled, unrelated to this A/B). `MinerviniBacktestService` = 11-year window

intervening month, expected). All numbers below are the `rs-turnover` variant (the live-funnel
analogue, M39's own convention) unless stated; portfolio figures are FIFO-gross and
RS-priority-NET (**"realistic-live"** — already net of the cost model above, satisfying "subtract

**Read-only against live, confirmed:** `MinerviniBacktestService.run(LocalDate)` issues only

## §1 — M36: the 50-day-MA trail arms unconditionally from day 1

### 1a. Confirming the audit's finding in the live engine, not just the backtest sim

**[computed]** The finding is real in BOTH the production exit engine and the deep-sim, independently:

- **Production** (`libs/strategy-engine/.../ExitEvaluator.java:659-671`, the `"indicator".equals(basis)`
  branch used by every Minervini `trailing_stop basis=indicator alias=sma50` rule): computes
  `level = indicatorLevel(bank, alias, index)` and fires the moment `close <= level`, with **no arm
  condition of any kind** — contrast the sibling `atr_multiple` branch three cases up
  (`ExitEvaluator.java:617-634`), which already supports an optional `arm_pct` that keeps an ATR
  trail inert until the position is up `arm_pct`% (the Manas §3.5B pattern) — the `indicator` basis
  has no analogous knob.
- **All four live Minervini strategy YAMLs** wire this same rule with zero extra params:
  `minervini-vcp.yaml:42`, `minervini-cheat-3c.yaml:44`, `minervini-power-play.yaml:39`,
  `minervini-primary-base.yaml:40` — all `{ type: trailing_stop, params: { basis: indicator, alias:
  sma50 } }`.
- **The deep-sim** (`MinerviniSwingBacktest.java:240-250`, pre-patch) mirrors this exactly:
  `exitFires` checks `close[i] <= sma50[i]` unconditionally once in a trade, with the 8% stop as the
  only other exit. The sim and the live engine agree — the sim is not inventing a stricter or looser
  doctrine than what ships.

So M36 is confirmed, not merely audit-alleged: **there is genuinely no arm-guard anywhere in the
current code**, live or backtest.

### 1b. The A/B

**Design:** baseline = current unconditional arm (byte-identical to production). Candidate = the
trail stays inert per (setup, symbol) trade until `sma50 >= entrySignalClose` at least once since
entry — a direct, literal operationalization of the decision sheet's own wording ("only begin
governing once the MA has caught up to (reached) the entry level"), and a single boolean condition
as the sheet recommended, not a threshold sweep.

### 1c. Results — per-setup (`rs-turnover` variant)

| setup | trades OFF→ON | Δtr | win% OFF→ON | payoff OFF→ON | exp%/trade OFF→ON | stopOut% OFF→ON |
|---|---|---|---|---|---|---|
| vcp | 7582 → 6962 | −620 (−8.2%) | 32.47 → 40.61 | 4.18 → 2.98 | 4.45 → 5.40 | 27.96 → 50.88 |
| primary-base | 7332 → 7133 | −199 (−2.7%) | 36.92 → 40.63 | 3.50 → 3.03 | 5.43 → 5.78 | 42.58 → 53.06 |
| cheat-3c | 5909 → 5491 | −418 (−7.1%) | 31.49 → 39.85 | 4.40 → 3.08 | 4.48 → 5.40 | 27.57 → 50.41 |
| power-play | 2325 → 2184 | −141 (−6.1%) | 32.00 → 38.05 | 5.19 → 3.93 | 6.85 → 7.80 | 32.65 → 53.89 |
| **ALL** | 23148 → 21770 | −1378 (−6.0%) | 33.58 → 40.17 | 4.10 → 3.11 | 5.01 → 5.76 | 32.96 → 51.78 |

**[computed]** The direction is consistent across all 4 independent setups (win% up, per-trade
expectancy up, payoff DOWN, stop-out rate up substantially, roughly ×1.6-1.9) — this is the "test the
robustness of any sign" check, and it passes at the per-trade level: this is a real, reproducible
mechanical effect, not noise in one setup. Mechanically it is exactly what disarming an early trail
should do: fewer premature whipsaw exits (win% up) but losers that don't recover before the trail
ever arms now ride to the full 8% stop instead of a smaller trailing-stop loss (stop-out rate nearly
doubles, payoff falls).

### 1d. Results — portfolio (8-slot)

| portfolio | CAGR% OFF→ON | maxDD% OFF→ON | Sharpe OFF→ON |
|---|---|---|---|
| FIFO gross | 22.90 → 33.94 | 43.74 → 42.86 | 0.63 → 0.78 |
| RS-priority NET *(realistic-live)* | 28.58 → 31.52 | 58.86 → 74.33 | 0.75 → 0.67 |

**[computed]** Here the sign-robustness check **fails**: FIFO-gross says "better" on all three
metrics; the realistic-live (RS-priority-NET, already cost-net) portfolio says CAGR is up modestly
(+2.94pp, +10.3% relative) but **maxDD is up 15.47pp (+26.3% relative, materially worse) and Sharpe
is down 0.08 (−10.7% relative)**. The verdict depends on which portfolio convention you read, and the
one this repo's own convention (M39's own table headers) labels "realistic-live" is the one that
comes out worse. A higher-CAGR/worse-Sharpe/worse-drawdown trade is not a clean win by the standard
the ledger already applies elsewhere (favour risk-adjusted return, not raw CAGR, on the realistic
portfolio).

### 1e. Recommendation

**Keep arm-day-1. Do not ship the tested "arm-once-MA-reaches-entry" fix.** The underlying mechanism
the audit flagged is real (§1c proves it), but the specific fix — simply withholding the trail until
the MA rises to the entry level — trades a CAGR bump for a much worse realistic-live drawdown and a
lower Sharpe. Because this is a delay/removal of an early protective exit trigger, it is a loosening
in spirit and the burden of proof is on it; it does not clear that bar. A differently-designed
successor (e.g. capping how much extra room the delayed trail can concede before some other guard
intervenes) might do better, but that is a new, uncosted design, not a decision this A/B can make —
flagging it as a possible future item, not recommending it.

## §2 — M37: Power Play's thrust precondition has no adjacency window to the base

### 2a. Confirming the audit's finding

**[computed]** `VcpDetector.thrust(bars, baseStartIdx)` (`VcpDetector.java:151-166`, pre-patch) scans
the ENTIRE `[0, baseStartIdx)` range for any qualifying low→high pair within `thrustWindow` (40)
sessions of each other; nothing bounds how close the qualifying pair itself sits to `baseStartIdx`.
A thrust from years before the current base still counts, exactly as the audit states.

### 2b. Step 1 — deploy-free geometry query over today's live screen

**[computed]** Latest screen `2026-07-31`: 115 `is_vcp=true` rows, 14 also `thrust=true` (today's live
Power Play population) — `marketdata.minervini_setups`. Recomputing each of the 14 with the exact
production `VcpDetector` (via the same `DailyBarReader`/`AdjustedEquityDailySql` source the live
screener uses, NOT the deep-sim's `candles` table — matching M39's own step-1/step-2 source split)
reproduced `thrust=true` for all 14 with **zero mismatches** against the live persisted flag — a
direct harness-validation check, not just a self-consistency one.

Sensitivity of that same population to a candidate adjacency cap:

| cap (sessions) | 30 | 60 | 90 | 120 | 180 | 250 |
|---|---|---|---|---|---|---|
| survive (of 14) | 5 (36%) | 13 (93%) | 13 (93%) | 14 (100%) | 14 (100%) | 14 (100%) |

**[computed]** At a "reasonable" cap (90-120 sessions, ≈4.5-6 months) this single-day snapshot says
almost nothing would change — only at a tight ≤60-session cap does it look restrictive. Taken alone
this would suggest skipping the deep backtest (the decision sheet's own escape hatch: "if the answer
is obviously '~all of them'..."). **It was wrong to stop here** — see §2d.

### 2c. Step 2 — deep backtest A/B (two magnitudes)

**Design:** baseline = current unconditional thrust (byte-identical to production). Two candidates:
a tight 30-session cap and a looser 90-session cap, bracketing the "high, tight flag" timing that
motivated testing this at all.

|---|---|---|---|
| FIFO gross — OFF | 22.90 | 43.74 | 0.63 |
| FIFO gross — cap30 | 29.29 | 58.66 | 0.64 |
| FIFO gross — cap90 | 22.76 | 35.15 | 0.65 |
| RS-priority NET *(realistic-live)* — OFF | 28.58 | 58.86 | **0.75** |
| RS-priority NET — cap30 | 22.69 | 64.76 | **0.63** |
| RS-priority NET — cap90 | 24.49 | 55.03 | **0.70** |

### 2d. Reading the numbers

**[computed]** The controls (`vcp`/`primary-base`/`cheat-3c`) are byte-identical across all three runs
— the cap touches only `power-play`'s entry gate, exactly as designed; the harness is scoped
correctly.

**The single-day snapshot (§2b) badly undersold the historical effect.** At the 90-session cap the
snapshot said "~93% of today's population survives, effectively no impact"; the 11-year deep
backtest shows the SAME 90-session cap cuts Power Play's trade count by **49.3%** and the tighter
30-session cap by **75.3%**. A 14-name, single-day cross-section is not the same population as an
11-year history — this is the sampling-window lesson this repo has hit before (a small snapshot can
differ hugely from the full distribution), and it argues for treating step-1 geometry queries as a
directional hint, never a substitute for the deep backtest, whenever the daily incidence of the
setup under test is this low (14/day here vs M39's 106/day for plain VCP).

**The sign is robust and it points the wrong way for a cap.** At BOTH tested magnitudes, the
realistic-live (RS-priority-NET) Sharpe falls: **0.75 (off) → 0.70 (cap90) → 0.63 (cap30)** —
monotonically worse as the cap tightens — and CAGR falls in both cases too (28.58 → 24.49 → 22.69).
Only `power-play`'s own per-trade payoff improves slightly under a cap (5.19 → 5.57/6.21), but that
improvement does not survive into the portfolio: removing the "stale-thrust" trades removes trades
that were net contributors to the realistic-live portfolio, not net detractors. Applying M39's own
decision rule verbatim ("caps-ON CAGR/expectancy ≥ caps-OFF ⇒ validate; else too aggressive",
`docs/strategies/m39-vcp-caps-backtest-2026-07-06.md:80-81`) to the realistic-live portfolio: caps-ON
is worse at both tested magnitudes ⇒ too aggressive at both.

### 2e. Recommendation

**Reject any thrust-adjacency cap; leave `VcpDetector.thrust()` unconditional.** The audit's concern
is real as a doctrine-purity observation (a "high, tight flag" is supposed to be tight in time, and
today's implementation does not enforce that), but empirically restricting it costs realistic-live
Sharpe and CAGR at every magnitude tested, the same shape of mistake M39 found in the VCP duration
floor: a plausible, doc-literal-sounding restriction that turns out to filter a population that was
paying for itself. No further tuning of the cap value is recommended — the direction is already
robust across a 3x range of candidate values (30 vs 90 sessions), so a third point is unlikely to
flip the conclusion (see Open Doubts §3 for the honest caveat on this extrapolation).

## Open doubts

1. **M36's drawdown-driver was not decomposed by year.** `PortfolioStat.annual` (year-by-year
   returns) was computed by the harness but not captured/printed in this pass, so I cannot rule out
   that the RS-priority-NET drawdown difference (58.86%→74.33%) is concentrated in one anomalous
   year rather than a broad-based effect. The 11-year peak-to-trough measure is already fairly robust
   to single-year quirks by construction, but this is not independently confirmed here.
2. **M36 has no true in-family control.** Unlike M37 (where `vcp`/`primary-base`/`cheat-3c` serve as
   an unaffected control since only `power-play` reads `thrust`), the trail change touches all 4
   Minervini setups identically — there is no unaffected Minervini setup to validate the harness
   against. Harness confidence instead rests on (a) the exact byte-identical baseline reproduction
   across two independent runs (§0), and (b) the fully consistent direction of the per-setup effect
   across all 4 setups (§1c) — a wiring bug would more plausibly produce an inconsistent pattern.
3. **M37's cap value (30/90 sessions) is [assumed], not sourced from doctrine.** Unlike M39's
   literal 60%/3-65-week thresholds (quoted directly from the strategy doc), the audit gives no
   specific adjacency number for M37 — I chose 30 (a tight "high, tight flag" reading) and 90 (a
   looser, several-month reading) to bracket a plausible range and test sign robustness, which held
   in both directions. A third point (e.g. 180 or 250 sessions, which the §2b snapshot suggests would
   look closer to "no effect" on a single day) was not deep-backtested; extrapolating that a looser
   cap would also be flat-to-negative rather than positive is reasonable given the monotonic trend
   already observed, but it is an extrapolation, not a measurement.
4. **No live paper-trade evidence was used for either item.** Both A/Bs are entirely historical
   (`candles`@1d, 2015-08-02 to present); the live Minervini paper book (enabled, running the
   20:00 IST daily batch) has not accrued enough closed trades to cross-check these effects on
   forward data, and this doc does not attempt to.
5. **Survivorship / universe caveats carry over from M39 unchanged.** Per
   `MinerviniBacktestService.run()`'s own note field (`MinerviniBacktestService.java:386-390`,
   confirmed by reading the source with this run's exact parameters substituted, not by printing it):
   "candles@1d ~11y over 8 concurrent slots; ... open-at-end positions dropped; portfolio is
   net-of-cost; survivorship-biased." The same caveats M39 disclosed apply verbatim here — this A/B
   inherits them, it does not introduce new ones.
6. **The temporary code toggles were reverted, not audited by a second reviewer.** The two additive
   static fields (`thrustAdjacencyDaysOverride`, `armTrailAtEntryOverride`) were removed before this
   PR was opened (git-diff-clean against `origin/main` on the production files); the PR ships
   docs + the ledger update only. The determinism/control checks in §0 are the evidence the toggles
   behaved as intended while they existed, since no reviewer can re-inspect code that no longer exists
   in the diff.
